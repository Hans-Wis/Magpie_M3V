§01

執行摘要

M3V 採 外掛式 domain（IP/npu/rtl/ ~1.6K 行 + 參數化 cpu_m1），Coral 採 單體 RvvCoreMiniAxi（~86K 行）。兩者軟體契約相近（CQ + mat + DMA 卸載），硬體拓撲不同。

議題判定說明
功能取代 Coral進行中TFLM int8 主幹已 e2e（gate_48/49/50）；RVV 子集、F、POOL 等未全綠
單發 vs 4-wide可接受Sequencer IPC 非瓶頸；mat 256 MAC/c 已對齊
最大架構差RVViterative vexu + 凍結 scalar；Coral 全 RVV backend + VCQ
Scalar F (IMF)延後int8 / Gemma PTQ 路徑不必急於 +F
外掛 cycle 開銷固定小常數每 MAT 指令多 ~10–30 拍 setup；非 256 參數線性暴增
外掛優勢SKU 彈性mat_engine 可參數化 LANES；易做 shadow launch / CQ 硬解碼
128-bit 統一Phase BDMA + ITCM line；見 §11；全系統 256b 不推薦
建議策略（已採納）：Phase A 功能完整（單發 + mat + RVV 契約）→ Phase B 效能（128b、流水、CQ 重疊、PPA）。不必為對標 Coral 改 4-wide scalar。

§03

與 Coral Kelvin 對照

Coral RvvCoreMiniAxi

  • 單體 ~86K LOC，206 modules
  • 4-wide in-order superscalar + scoreboard
  • RV32IMF + 完整 rvv_backend_*
  • 硬體 VCQ（depth 8）→ RVV mac_unit
  • 128-bit AXI + 128-bit TCM
  • datasheet: 256 MAC/cycle

M3V 外掛 NPU

  • domain ~1.6K + 參數化 cpu_m1
  • 單發 4-stage stripped sequencer
  • RV32IM + vexu 子集（F deferred）
  • 外掛 mat_engine + 系統 CQ ring
  • 32-bit AXI + 2×256b TCM eng 埠
  • 實測 256 MAC/c（ADR-0040）

Cycle 評估

6.1 控制延遲（外掛 vs Coral）

項目M3V 粗估說明
CSR 寫 → mat_go+1～2 拍registered pulse；非 AXI 額外延遲
CSR 讀（poll）+1 拍core_csr_rd_pending
MAT.OP setup~12–20 拍3× sw（A/B/CTRL）；單發
MAT.OP compute≤ ceil(rpt/4)+6例 rpt=64 → ≤22 拍；與 Coral stripmine 同語義
「256 MAC/cycle」≠ 256 個參數。RPT 一次帶入重複次數；CSR 固定 ~3～8 個暫存器。不會因 256 MAC 能力而線性增加 setup 週期。

6.2 重疊潛力（現況 vs 可優化）

§07

PPA / TSMC 28nm 頻率

Latency（多幾拍）與 Fmax（能跑多快）無直接因果。外掛 CSR 多 1 拍暫存反而有利時序切分。

區塊對 Fmax 影響備註
cpu_m1 單發可能較易DC trial ~699 MHz（僅 cpu_m1_top，28HPC+）
Coral 4-wide控制面複雜DispatchV2 + scoreboard 大
mat_engine可能瓶頸單拍 256 MAC 組合樹；宜流水化（Phase B）
npu_top 整體not-run需 synthesis signoff
§08

mat_engine 彈性與 SKU

外掛 mat_engine 較 Coral 單體更易做 MAC 規模 SKU；受 TCM bank 頻寬（ADR-0044）約束。

建議微架構演進（外掛）

  • A. 維持外掛 + MAC 流水（衝 Fmax）
  • B. 參數化 LANES（64/128/256）
  • C. 不建議整顆改 Coral 單體

Coral 開源 emit

  • MAC 綁 rvv_backend_mac_unit
  • 獨立 mat SKU 難
  • 語義：8×8 × 4 issue = 256

外掛 Cycle 改善方案

256-bit CSR 僅在搭配「一次 commit」時有意義；光加寬、store 次數不變則 ROI 低。

優先方案預估節省改動面

§10

分階段開發計畫

Phase A — 功能完整（維持單發）

  1. RVV 補齊mask / strided / saturating / LMUL + lockstep
  2. TFLM op 擴充POOL、Attention 相關；Gemma 270M 走 int8 PTQ，+F 非必須
  3. 大模型 tile 正確性DMA 分塊 streaming；權重 >> DTCM

Phase B — 效能（功能 regression 全綠後）

  1. MAT_SHADOW + COMMIT減 CSR setup cycles
  2. 128-bit 統一資料面詳見 §11：DMA + ITCM line fetch
  3. CQ 異步流水 + IRQ
  4. mat MAC 流水 + RVV issue buffer
  5. npu_top TSMC28 synthesis signoff
刻意不做（scope-cut）：4-wide scalar、Coral 單體 port、clock gating（至 Phase 7）、device 端 RING_OVERRUN 偵測。
§11

128-bit 統一匯流排 — 改善方案與效果評估

建議採 「資料面 128-bit 統一」：DMA/DTCM 資料搬運 + ITCM 128-bit line fetch；CSR 維持 32-bit AXI4-Lite；mat_engine 保留 2×256-bit 專用埠。不建議全系統一次升到 256-bit。

與 Coral 4×32 預取的關係：128-bit ITCM line = 一次 16B（4 條 32-bit 指令），對齊 Coral fetch line width；但要接近 Coral IPC 還需 4-wide issue（本線 Phase B 不做，sequencer 角色不需要）。

11.4 為何不做全系統 256-bit

128-bit 統一（推薦）

  • 對齊 Coral datasheet 128-bit 記憶體埠
  • ITCM line = 4×32，剛好滿足預取 line
  • mat 2×256b 專用埠已覆蓋 256 MAC 餵料
  • 28nm 時序/面積風險可控

256-bit 全系統（不推薦）

  • ITCM 256b = 8×32，單發/4-wide 均過寬
  • CSR poll 背負寬匯流排，浪費動態功耗
  • 與 Coral 128b 規格偏離，難宣稱對等
  • 512+ MAC 應走 LANES/多 engine，非拉 AXI

11.5 與其他 Phase B 項目的協同

組合綜效
128b DMA + CQ 異步流水mat 算當前 tile 時，DMA 載下一 tile；端到端 最大收益
128b DMA + MAT_SHADOW搬運與 setup 同時縮；互補
128b ITCM + 單發取指略快；不能替代 RVV/mat 優化
僅 128b、仍同步 wait只有 DMA 段變快；收益 打折
