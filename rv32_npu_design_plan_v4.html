00

概觀

本規劃描述一個雙核 SoC:RV32IMC 主機負責應用邏輯與排程,RV32-based NPU 負責 ML 推論。兩者以 AXI4 解耦——主機透過記憶體映射暫存器設定與觸發 NPU,NPU 以自己的 DMA 主埠讀寫共享記憶體。

NPU 的內部結構參考 Coral NPU:它反轉傳統處理器設計,以矩陣引擎為中心,scalar 核退居控制前端角色。三個運算元件——scalar(控制)、vector(標準 RVV / Zve32x)、matrix(自訂 outer-product MAC)——由 scalar 核透過 command queue 驅動。Coral 的公開目標數字為 512 GOP/s @ 256 MAC/cycle、~6 mW(22 nm),本設計以此為 datapath 參考基準。

關鍵解耦:主機的 RV32IMC 與 NPU 內部的 scalar 控制核是兩顆不同的 RV32 核。前者跑應用(可含壓縮指令 C),後者是無中斷的 run-to-completion executor,只負責把工作餵進向量/矩陣後端。AXI 是它們唯一的契約面。
01

系統架構

AXI4 crossbar 居中,掛三個 agent:主機(manager)、NPU(既是 subordinate 供設定、也是 manager 供 DMA)、共享記憶體(subordinate)。控制路徑走 AXI-Lite(暫存器/doorbell),資料路徑走 AXI-Full(突發 DMA)。NPU 完成後以中斷線回報主機。

02

NPU 微架構

NPU 內部是「scalar 前端當控制器,驅動向量/矩陣後端 command queue」。下圖依 Coral NPU 官方結構繪製,每個執行單元的數量都標示在圖上:scalar 前端每 cycle 取一束指令進 instruction buffer,4-way decode/dispatch(scoreboard 擋 hazard)分派到 4 組 ALU+BRU、1 個 MUL、1 個 DIV 與 LSU;向量指令經 Vector Command Queue 解耦後餵給 2 個 Vector ALU;矩陣工作經 Matrix Command Queue 驅動 256 MAC/cycle 的 outer-product 陣列。

執行單元數量一覽(客戶速查)

單元數量規格 / 行為
Scalar ALU×4每個 dispatch lane 一個;1-cycle latency
BRU(分支)×4靜態預測:backward taken / forward not-taken;猜錯付 1 cycle
MUL×13-stage pipelined;每 cycle 最多 1 條乘法
DIV×1非管線化(iterative);busy 時 backpressure 擋分派
LSU / Vector LSU×1每 cycle 1 筆 memory op;向量載存共用埠
Scalar Regfile1x0–x31,多埠 8 read / 6 write
Vector ALU×22-way vector dispatch;標準 RVV 1.0 / Zve32x
Vector Regfile32×128bVLEN = 128
MAC 陣列256/cycleint8×int8 → int32 accumulate;acc 8×8×32b;≈512 GOP/s
ITCM / DTCM8 / 32 KBsingle-cycle SRAM,scalar 核私有
吞吐怎麼讀:4-way dispatch 是「上限」——ALU/BRU 夠每 lane 一個,但 MUL、DIV、記憶體都是單發資源。實際 IPC 由指令組合與 scoreboard 相依決定;ML 主力吞吐不在 scalar 前端,而在右側 256 MAC/cycle 的矩陣陣列。scalar 前端刻意保持最小(run-to-completion、無 speculation),把面積與功耗預算讓給 MAC——這正是 Coral「反轉傳統處理器」的核心。
03

AXI 互連與 Offload 協定

主機與 NPU 的分工透過兩類 AXI 交易表達:控制面(AXI-Lite,主機寫 NPU 暫存器)與資料面(AXI-Full,NPU 自主 DMA 突發)。offload 一次推論的協定如下:

階段發起者AXI 交易內容
SETUPHost M0Lite 寫把 model image + input tensor 佈到共享記憶體,設定 NPU 的 base 指標暫存器
DOORBELLHost M0Lite 寫寫 CTRL.START=1(doorbell),觸發 NPU scalar 核
FETCHNPU M1Full 讀scalar 核經 DMA 突發讀入 command buffer / 權重到 TCM
COMPUTENPU 內部—command queue 驅動 RVV / 矩陣引擎,accumulator 累加
WRITEBACKNPU M1Full 寫結果 tensor 突發寫回共享記憶體
DONENPUIRQ拉中斷線;主機讀 STATUS 取回結果指標
為什麼用 AXI 解耦而非緊耦合:主機與 NPU 有各自的時脈/功耗域,AXI 讓 NPU 可獨立 gating(always-on 場景下主機睡、NPU 醒)。代價是 doorbell/IRQ 的延遲,對批次張量工作可忽略;若要做細粒度 per-op 卸載,才需考慮緊耦合(如把矩陣引擎直接掛進主機的 command queue)。
04

NPU 內部 TCM 為私有、single-cycle;對主機曝露的是一組控制/狀態暫存器(AXI-Lite 視窗)。共享記憶體是雙方 DMA 的交會點。

區域Base(範例)大小存取說明

05

TensorFlow → 可執行檔 編譯流程

從 Python 模型到跑在 NPU 上的 binary,有兩條互通路徑:LiteRT(TFLite)轉換器路徑,與 MLIR / IREE 路徑。兩者最終都收斂到 MLIR,經 IREE 的硬體專屬 plugin 做漸進下降(progressive lowering)——逐層把高階 tensor 語意翻譯到愈來愈接近機器碼的 dialect,最後產出目標 binary。

逐步說明

  1. 建模(Python):TensorFlow/Keras 訓練模型(JAX、PyTorch 同理)。
    此層是純軟體,決定運算圖與精度需求。
  2. 轉 LiteRT + 量化:以 TFLiteConverter 轉成 .tflite,用 representative dataset 做 post-training int8 量化。
    量化是 NPU 效能關鍵——矩陣引擎吃 int8→int32,浮點路徑僅供 fallback。
  3. Import 到 MLIR:經 StableHLO(或由 LiteRT 轉 TOSA)進入 MLIR 世界,取得可跨 dialect 優化的中介表示。
  4. IREE + NPU plugin:硬體專屬 plugin 讓編譯器「認得」本 NPU 的 command-queue、RVV、矩陣 op;啟動 progressive lowering。
  5. Tiling / stripmine:把大 tensor op 切成符合 accumulator 尺寸與 VLEN 的區塊,產生 command queue 序列(對齊 §02 的 stripmine 機制)。
  6. Codegen:下降到 RVV + scalar 組語 dialect,經 LLVM/RV32 後端 codegen 成 code + command stream,連結成 .elf。
  7. 部署:主機把 binary 佈到 SHARED_MEM,寫 doorbell 觸發——進入 §07 的執行期資料流。

貫穿範例:同一個 Dense 從兩條路走到 binary

用同一個最小模型(一層 Dense(64) + ReLU,本質就是 int8 matmul)貫穿全程,可以看到兩條路徑其實是前段不同、中段收斂(都進 MLIR)、後段共用(同一套 progressive lowering)。

路徑 A · LiteRT/TFLite 轉換器量化在「轉換」那一刻定案

Python 端轉換 + PTQ int8,量化語意直接凍進 flatbuffer:

# model = Dense(64, relu)
conv = tf.lite.TFLiteConverter.from_keras_model(model)
conv.optimizations = [tf.lite.Optimize.DEFAULT]
conv.representative_dataset = rep_ds          # 校準用真實輸入
conv.target_spec.supported_ops = [tf.lite.OpsSet.TFLITE_BUILTINS_INT8]
conv.inference_input_type = tf.int8; conv.inference_output_type = tf.int8
open("dense.tflite","wb").write(conv.convert())

.tflite 裡凍結的量化契約(跟 MAC 陣列 i8×i8→i32 一對一):

FULLY_CONNECTED (fused RELU)
  input   : int8 [1,64]   scale=0.0392  zp=-128
  weights : int8 [64,64]  scale=0.0074  zp=0
  bias    : int32[64]     scale = 0.0392 x 0.0074   <- bias 是 int32
  output  : int8 [1,64]   scale=0.0561  zp=-128

import 進 MLIR(TOSA dialect):iree-import-tflite dense.tflite -o dense_tosa.mlir

%acc = tosa.matmul  %x, %w   : (tensor<1x64xi8>, tensor<64x64xi8>) -> tensor<1x64xi32>
%b   = tosa.add     %acc, %bias
%r   = tosa.rescale %b {multiplier = 1422158234 : i32, shift = 38 : i8}
%out = tosa.clamp   %r {min_int = -128, max_int = 127}   # fused ReLU + saturate

tosa.rescale 把浮點 M = s_in·s_w / s_out ≈ 0.00517 編成 Q31 定點乘法 + 右移 38(1422158234 / 2³⁸ ≈ 0.00517)。這個 multiplier/shift 就是硬體必須 bit-exact 實作、且不吃容差的部分。

路徑 B · StableHLO / IREE適合 JAX / PyTorch

同一個運算從 JAX 出發,入口 IR 是純 tensor 數學、完全不知道硬體:

# def f(x,w,b): return jax.nn.relu(x @ w + b)  → jax.export → StableHLO
%0 = stablehlo.dot_general %x, %w,
       contracting_dims = [1] x [0]
     : (tensor<1x64xf32>, tensor<64x64xf32>) -> tensor<1x64xf32>
%1 = stablehlo.add     %0, %b
%2 = stablehlo.maximum %1, %zero      # ReLU

兩條路到這裡收斂:不論入口是 TOSA 還是 StableHLO,接下來都是同一條命令——

iree-compile dense_tosa.mlir \
  --iree-hal-target-backends=<NPU-plugin> -o dense.vmfb
Progressive lowering · 同一個 matmul 逐層下降L1 → L5 → binary

每一層只知道它該知道的事;「matmul」的抽象逐步被硬體語意取代:

// L1 · linalg —— 結構化運算,仍是 tensor
linalg.matmul ins(%A,%B : tensor<1x64xi8>,tensor<64x64xi8>) outs(%acc : tensor<1x64xi32>)

// L2 · tiling —— 第一次「知道硬體」:切成 8x8 = accumulator 尺寸
scf.for %j = 0 to 64 step 8 {          # 8 = acc 寬
  scf.for %k = 0 to 64 step 8 {        # 8 = acc 深
    linalg.matmul ins(%A[0,%k][1,8], %B[%k,%j][8,8]) outs(%c_acc) }}  # 一個 8x8 tile

// L3 · matrix dialect —— 只剩 command queue 語意(= §06 spec)
%q0 = npu.acc.alloc : !npu.acc<8x8xi32>
npu.mat.outer_product %q0, %a_col, %b_row {stripmine = 4}   # 1 dispatch → 4 issue
%r  = npu.vec.rescale %q0 {multiplier = 1422158234, shift = 38} : i8
npu.cmdq.post %r to @matrix_queue

// L4 · assembly dialect —— 一對一貼近機器
npu.asm.emit_cmd %buf[%idx], opcode = MAT_OP, acc = 0, rpt = 4
riscv.vsetvli t0,a2,e8,m1 ; riscv.vle8.v v1,(a0)     # 週邊向量走標準 RVV

// L5 · LLVM/RV32 codegen → 連結 → dense.elf(code + command stream)

到 L3,「matmul」已經不存在,只剩我們 command queue 的 op——這一層的 op 集合就是 §06 的編碼 spec,同時是 RTL 解碼器、編譯器 backend 目標、與數值 golden model 的共同介面。

與硬體設計的接點:Tiling / stripmine → command queue 這一步,是編譯器與 §02 command-queue 硬體格式的契約面。硬體的 command 編碼一旦定案,就成為編譯器 backend 的目標 ISA;兩邊要用同一份 spec——這份 spec 就是 §06 的 Command 編碼 Spec。
06

Command 編碼 Spec v0.1

這一節把 §05 的 npu.mat.* dialect 落成實際的 bitfield 定義。它是四位一體的單一真值:同一份定義同時是 (1) RTL command 解碼器、(2) IREE backend 的 codegen 目標、(3) 矩陣引擎數值 golden model 的介面、(4) assembler 的編碼表。任一邊改動都必須改這份 spec。

Command descriptor · 128-bit(4 × 32-bit word)

所有 command 共用 W0 表頭;W1–W3 為 union,語意依 opcode 而定。

W0 bits欄位說明
[5:0]OPCODE操作碼,見下表
[7:6]DTYPE00=int8 · 01=int16 · 10=bf16
[11:8]ACCaccumulator bank id(0–15,對應 8×8×32b 各 bank)
[12]IRQ完成時拉中斷 / 置 done flag
[13]FENCE先排空所有前序 command 才發此筆
[14]LASTtile group 的最後一筆
[23:16]RPTstripmine / 序列化 issue 數(預設 4)
[31:24, 15]rsvd保留(須為 0)

Opcode 表(v0.1 · 矩陣佇列)

opcodemnemonicW1 / W2 / W3對應 dialect op
0x01MAT.CFG(M<<16)|N / K / tile_flagsacc.alloc + 幾何設定
0x02MAT.LOAD_Wsrc_addr / stride / (rows<<8)|colsweight 進陣列(stationary)
0x03MAT.OPa_addr / b_addr / (acc_r<<4)|acc_cnpu.mat.outer_product
0x04MAT.RESCALEmultiplier / shift+zp / clampnpu.vec.rescale(tosa.rescale)
0x05MAT.STOREdst_addr / stride / (rows<<8)|colsnpu.cmdq.post(結果)
0x06MAT.ACC_CLRacc_mask / — / —accumulator 清零
0x07MAT.FENCE— / — / —與 scalar 核同步 / 完成旗標
MAT.OP 語意:對 ACC bank 執行 RPT 次序列化 outer-product 累加(int8×int8 → int32),每次依 stride 前進 a/b 指標——這就是硬體端的 stripmine 展開(1 dispatch → 4 issue)。矩陣主吞吐全在這一個 opcode。

MAT.RESCALE:唯一「不吃容差」的欄位

這是 tosa.rescale 的硬體對應,把 int32 累加值 requantize 回 int8。採 TFLite/ARM 風格定點:Q31 multiplier × rounding-right-shift,最後 clamp。golden model 對這一步必須 bit-exact(其餘 tensor 值才吃容差)。

# out_i8 = clamp( RoundingShiftRight(acc_i32 * multiplier, shift) + out_zp )
W1 = multiplier (Q31)   = 0x54C4699A   # = 1422158234 ≈ 0.6621 x 2^31
W2 = (out_zp << 8) | shift = 0x8026            # shift = 38 (0x26), out_zp = -128
W3 = (clamp_max << 8) | (clamp_min & 0xFF) = 0x7F80   # [-128,127]

下降對照:L3 dialect → command stream

把 §05 的 L3 片段編成實際 128-bit command(hex,W0..W3):

npu.acc.alloc                          -> MAT.ACC_CLR  W0=0x00000006  W1=0x0001 (mask)
npu.mat.outer_product {stripmine=4}    -> MAT.OP       W0=0x00040003  W1=a_addr W2=b_addr W3=0
   # W0: op=0x03, DTYPE=00(i8), ACC=0, RPT=4 (0x04<<16)  →  0x00040003
npu.vec.rescale {mult=…,shift=38}      -> MAT.RESCALE  W0=0x00000004  W1=0x54C4699A W2=0x8026 W3=0x7F80
npu.cmdq.post                          -> MAT.STORE    W0=0x00005005  W1=dst   W2=stride W3=(rows<<8)|cols
   # W0: op=0x05, LAST(bit14)+IRQ(bit12) 置位  →  0x00005005
v0.1 已凍結 vs 尚待決策:已凍結——128-bit 定寬 descriptor、opcode 0x01–0x07、MAT.RESCALE 的 Q31+shift 定點契約。尚待決策——ACC bank 數(暫 16)、DTYPE 是否納 bf16(視 §00 算力路徑)、向量佇列(npu.vec.*)的 opcode 空間(本版僅定義矩陣佇列)。凍結欄位變更需走 §08 的 design-change gate;新增 opcode 屬 config-level。
07

執行期資料流

一次推論在硬體上的生命週期,把 §03 的 offload 協定與 §02 的內部結構串起來:

  1. 主機佈資料:RV32IMC 把量化後的權重/輸入寫進 SHARED_MEM,設定 NPU 的 base 指標暫存器。
  2. Doorbell:主機寫 CTRL.START,喚醒 NPU scalar 控制核。
  3. 取 command:scalar 核經 DMA(AXI M1)突發讀入 command buffer 與權重到 TCM。
  4. 分派:command queue 驅動 RVV 向量與矩陣引擎;stripmine 把一次 dispatch 展成多筆序列化 issue。
  5. 累加:矩陣引擎做 outer-product,int8 乘積 reduce 進 32-bit accumulator;向量核處理 activation/pooling 等週邊。
  6. 寫回:結果 tensor 經 DMA 突發寫回 SHARED_MEM。
  7. 中斷:NPU 拉 IRQ;主機讀 STATUS、取回結果,或排下一個 tile。
08

驗證與簽核

兩條驗證軌,對應兩種 golden model:

子系統Golden model方法
Host RV32IMCSpike(有 ISA)RVFI lockstep + riscv-dv
NPU scalar / RVVSpike + vector(有 ISA)RVVI/RVFI lockstep · 狀態爆炸 coverage
Matrix engine無 ISA · 需自建bit-accurate 數值 ref + tensor 級容差/量化比對
AXI 互連—AXI VIP / 協定檢查 · doorbell-IRQ 時序
端到端TFLite reference整機模型推論容差比對
單一真值原則:command queue 的編碼格式必須是編譯器 backend 與 RTL 共用的同一份 spec。這份 spec 同時餵 (1) RTL 參數、(2) IREE plugin 的 codegen、(3) 矩陣引擎的數值 golden model——三邊一致才不會出現「編出來的 command 硬體不認得」的整合裂縫。雙軌 sign-off:開源軌 Verilator + cocotb,商用軌 VCS + Spyglass。
最需新建的一塊:矩陣引擎沒有 ISA golden model,那條 tensor 級數值驗證軌是本專案唯一需要從零建的驗證能力,建議由與實作隔離的獨立鏈撰寫,避免共模錯誤。
