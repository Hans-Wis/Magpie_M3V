The biggest immediate blocker is worse than “missing harness”: [gemma_quant.py](/home/edauser/project/SOC/Magpie_M3V/design/npu/sw/gemma/gemma_quant.py:30) does not exactly match the proven `mat_engine`/`mat_golden` SRDHM rounding for negative products.

**Critical finding:** `gemma_quant.srdhm()` uses Python `>>` after nudge ([gemma_quant.py:30-35](/home/edauser/project/SOC/Magpie_M3V/design/npu/sw/gemma/gemma_quant.py:30)), while the matrix authority explicitly truncates negative division toward zero ([mat_golden.py:40-48](/home/edauser/project/SOC/Magpie_M3V/design/npu/golden/mat_golden.py:40)) and RTL implements that same negative path ([mat_engine.v:132-135](/home/edauser/project/SOC/Magpie_M3V/design/npu/rtl/mat_engine.v:132)). When I replayed S0 using `mat_golden.rescale`, the current deterministic S0 case changed `gate_q` by 1 byte, `up_q` by 1 byte, `prod_q` by 16 bytes, and final `out_q` by 85/256 bytes. So S0 golden is not currently bit-exact to RTL.
