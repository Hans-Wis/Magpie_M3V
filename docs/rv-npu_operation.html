00

三引擎分工總覽

三個引擎不是「三顆一樣的核」,而是三種針對不同運算結構的機器。開發者不手動分配——是編譯器 backend 在 lowering 時,依運算的結構自動判給對應引擎。

引擎負責典型運算指令來源
Scalar控制:位址、迴圈、分支、發 command、同步loop / addr-gen / branch標準 RV32IM
Vector逐元素:活化、bias、requantize、poolingrelu / add / rescale / pool標準 RVV(Zve32x)
Matrix沿軸累加:矩陣乘、卷積主體matmul / conv / QKᵀ自訂 command(非 ISA)
01

判準原理:contraction 軸

「contraction(收縮)」是線性代數概念:兩個張量相乘時,有一個維度被『加掉』而在輸出裡消失。那個消失的維度,就是 contraction 軸。它是否存在,直接決定硬體需不需要一個「反覆累加的累加器陣列」。

以矩陣乘為例:

C[i,j] = Σk A[i,k] · B[k,j]    # k 在輸入裡有,在輸出 C 裡消失了

A 是 [i,k]、B 是 [k,j]、C 是 [i,j]。k 被 Σ 吃掉了——這就是 contraction 軸。「沿 contraction 軸累加」= 對 k 從頭掃到尾,把每個 A[i,k]·B[k,j] 一項項加進同一個累加器,直到 k 掃完才得到一個 C[i,j]。這正是 MAC(乘-累加)的本質:乘完立刻累加,累加器不清空。

對比 element-wise(如 ReLU):輸入形狀 = 輸出形狀,沒有任何維度消失,每個輸出只看對應位置的輸入,不需要累加器。

為什麼這對硬體是天壤之別

Contraction(matmul)——累加器是主角。算一個 C[i,j] 要掃完整條 k,期間累加器持續累加、不能清空;而且同一個 A[i,k] 被不同 j 重用、B[k,j] 被不同 i 重用——大量資料重用。矩陣引擎(outer-product / systolic)就是為「讓資料在陣列裡流動、最大化重用、把累加留在原地」而生。int8×int8 的積會變大,所以累加器要 int32——這正是量化契約 i8→i32 的由來。

Element-wise(ReLU)——沒有累加,沒有重用。每個元素讀一次、算一次、寫一次,彼此獨立。RVV 的 vmax/vadd 一次處理一整排就完美對上;用矩陣引擎反而讓累加器閒置、浪費。

卷積也是 contraction,只是軸更多:Out[n,y,x,f] = Σ_c Σ_kh Σ_kw In[…]·W[…]——輸入通道 c 與 kernel 窗 kh,kw 三個軸一起被加掉。所以卷積本質與 matmul 同類,編譯器常用 im2col 或直接 lower 成 matmul,走矩陣引擎。
reduction 是中間態:pooling 的 sum/max、softmax 的 Σ 也有「軸消失(有累加)」,但沒有『乘』的資料重用結構,不值得動用 MAC 陣列 → 走 Vector 核的 reduction 指令。判準的完整版是:有累加 且 有乘法重用 → Matrix;只有累加 → Vector reduction;都沒有 → Vector element-wise。
02

身分差異:指令 vs command

三引擎最容易被誤解的一點:Vector 走「指令」、Matrix 走「command」——這是兩種不同身分的東西。搞混會讓人以為要去改 scalar 核的指令解碼器(IDU),其實不用。

Vector(指令)Matrix(command)
本體真正的 RISC-V 指令(vmax…)寫進記憶體的 128-bit descriptor
編碼放哪指令流,標準 Zve32x opcodecommand buffer(記憶體資料)
誰解碼scalar 核的 IDU(標準 decoder)矩陣引擎自己的 command decoder
怎麼發執行一條指令用標準 sw 寫一筆資料
動到 ISA?否(用標準指令)否(不佔 opcode)

所以 scalar 核「發射」一個矩陣操作,實際上就是幾條標準 store 指令把 descriptor 寫進 command queue——沒有任何非標準指令。矩陣引擎在自己的邊界內,用自己的 decoder 讀那份 descriptor 動作。自訂的是「command 編碼」,不是「指令集」。

兩個 decoder,別混為一談:scalar 核的 IDU 只認得 RV32IM + RVV,它看到寫 descriptor 的 sw 只解成一個普通 store;矩陣引擎的 command decoder 才解 descriptor、產生 MAC 控制訊號。兩者唯一的接觸點是記憶體裡那份格式,不共用解碼邏輯。也因此矩陣引擎對 RV32 compiler 完全透明——標準組譯器/連結器/Spike 都不知道它存在。
03

一個 op 如何裂成三股

把判準套到具體:一個 fused Dense + ReLU,被編譯器自動拆成三引擎的三股,最後交織在同一個 .elf 裡。

// scalar 核執行的主體(RV32IM),三種東西交織
for (int j=0; j<N; j+=8)              // Scalar:tile 迴圈 / 位址
  for (int k=0; k<K; k+=8)
    *cmdq = MAT_OP(acc0, &A[k], &B[k][j], 4);   // Matrix:標準 sw 寫 command
  *cmdq = MAT_RESCALE(mult, shift, clamp);
  mat_wait(acc0);                            // Scalar:fence 同步
  asm("vle8.v v1,(%0); vmax.vx v1,v1,zero; vse8.v v1,(%1)"
      ::"r"(acc_out),"r"(dst));               // Vector:標準 RVV,ReLU
04

協作與同步

拆給三引擎後,資料要接得起來,靠兩種機制:

1 · Scalar ↔ Matrix:fence 等待

scalar 發完 MAT.OP 後不能馬上讀結果——矩陣引擎與前端是 FIFO 解耦、非同步的。scalar 用 MAT.FENCE + 輪詢 status,或完成中斷,確認 tile 算完才往下走。這就是程式裡的 mat_wait()。

2 · Matrix → Vector:記憶體交接

矩陣的 int32 結果落在 accumulator / DTCM tile buffer,向量核再用 RVV 從那個記憶體位址讀出來做 rescale + ReLU。交接點是記憶體,不是暫存器——這也是為什麼三引擎能各自獨立、只靠共享記憶體協作。

3 · 順序正確性:編譯器保證

IREE 在 lowering 時就把相依性排好:rescale 一定排在對應 matmul 的 fence 之後、vector ReLU 一定排在 rescale 之後。產出的指令 / command 順序天然正確,執行期不需要動態排程。

為什麼這樣分工能省能耗:非同步解耦讓三引擎可各自 gating——矩陣陣列忙時,scalar 前端幾乎閒置(它只是發 command);向量核只在 rescale/activation 階段醒。加上矩陣走 command(免逐指令 fetch/decode),把能耗預算集中到真正做 MAC 的地方。這正是 Coral「反轉傳統處理器」在能效上的回報。
05

為什麼是兩條驗證軌

§02 的「身分差異」有一個直接後果:驗證必然分兩條軌,這不是選擇,是結構的必然。

子系統身分有 ISA golden model?驗證方法
Scalar標準指令有(Spike)RVFI lockstep + riscv-dv
Vector標準 RVV 指令有(Spike vector)RVVI/RVFI lockstep · 狀態爆炸 coverage
Matrixcommand(非 ISA)無bit-accurate 數值 ref + tensor 級容差比對

Scalar 與 Vector 走標準指令,所以 Spike 認得它們、能逐指令 lockstep。Matrix 走 command、根本不在 ISA 裡,Spike 本來就看不到它——所以它必須走獨立的數值 golden model 軌,用 tensor 級容差比對,其中 MAT.RESCALE 的定點 requantize 是唯一必須 bit-exact 的部分。

一句話收束全篇:一條判準(有無 contraction 軸)決定了引擎分工;引擎分工決定了指令 vs command 的身分差異;身分差異決定了兩條驗證軌。整個 RV-NPU 的結構,都是從「這個運算有沒有沿一個軸把東西加掉」這一個問題長出來的。
