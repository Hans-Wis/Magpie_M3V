WHYWhere the cycles went

The baseline cost is dominated by per-tile software orchestration, not compute. The acceleration removes that overhead, then trims redundant data movement — the actual matrix compute is unchanged throughout (proving identical results).

SKUMAC-array tiers — area / power, customer-selectable

The MAC array is a synthesis-time parameter. Because typical edge inference (batch-1 token decode) is memory-bandwidth-bound, a smaller array runs it at nearly the same speed with materially lower area and power — while a larger array serves compute-heavy (prefill / batched) workloads. All tiers are bit-exact and meet the same clock.

METHODHow these numbers are produced

Correctness

Every accelerated path is run on the RTL and compared byte-for-byte to the int8 quantized reference. No result is accepted on inspection or a passing lint — only on a bit-exact match.

Performance

Cycle counts are measured in RTL simulation (start→done), decomposed into compute / data-movement / control. Area and power come from a real Synopsys DC + TSMC 28 nm flow, not estimates.

SCOPEReading these figures

  • Representative dimensions. The GEMM trajectory is measured on a representative projection (K=64, N=64) at small sequence length — the mechanism is dimension-independent; absolute cycles scale with the model's layer sizes.
  • Scope of the 5.5×. It is the compute-offload path for the matrix (GEMM) work — the dominant repeated primitive. Non-matrix (normalization, activation) runs on a separate vector path and is optimized independently.
  • Floor is physical. Past ~5.5× the remaining cost is weight streaming from memory, which is bandwidth-bound; further gains come from bandwidth, not orchestration.
  • All measured. Cycle figures are RTL-measured; PPA is real 28 nm synthesis. Projections, where any appear, are labeled as such in the underlying reports.
