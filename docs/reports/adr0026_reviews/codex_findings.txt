Current `mul.v` is 2-cycle start/done with no accept-ready pipeline: `start && !busy`, then `busy`, then `done_pending` ([IP/cpu_m1/rtl/mul.v:59](/home/edauser/project/SOC/Magpie_M1A/IP/cpu_m1/rtl/mul.v:59), [IP/cpu_m1/rtl/mul.v:62](/home/edauser/project/SOC/Magpie_M1A/IP/cpu_m1/rtl/mul.v:62), [IP/cpu_m1/rtl/mul.v:68](/home/edauser/project/SOC/Magpie_M1A/IP/cpu_m1/rtl/mul.v:68)). The core globally stalls while the same ID instruction is mul/div: `md_busy = if_ex_valid && id_is_muldiv && !md_result_valid` ([IP/cpu_m1/rtl/core.v:662](/home/edauser/project/SOC/Magpie_M1A/IP/cpu_m1/rtl/core.v:662)); hazard turns that into `muldiv_stall` ([IP/cpu_m1/rtl/hazard.v:54](/home/edauser/project/SOC/Magpie_M1A/IP/cpu_m1/rtl/hazard.v:54)). A1 needs explicit new issue/scoreboard/consumer-bypass gates, not just “lockstep + MACSTREAM delta.”

2. **HIGH - The “not combinational 1-cycle” rationale is technically muddled against existing RTL.**  
   Evidence: ADR rejects “combinational 1-cycle (32x32 in 1.43 ns)” ([docs/adr/0026-m1a-performance-scope.md:30](/home/edauser/project/SOC/Magpie_M1A/docs/adr/0026-m1a-performance-scope.md:30)), but current `mul.v` already performs the 33x33 multiply combinationally between operand/result flops: `product_w = opa_r * opb_r` and result latched in the next cycle ([IP/cpu_m1/rtl/mul.v:37](/home/edauser/project/SOC/Magpie_M1A/IP/cpu_m1/rtl/mul.v:37), [IP/cpu_m1/rtl/mul.v:69](/home/edauser/project/SOC/Magpie_M1A/IP/cpu_m1/rtl/mul.v:69)). The proposed improvement should be framed as decoupling/pipelining issue and result forwarding, not avoiding an internal one-cycle multiplier path that already exists in the frozen baseline.

3. **HIGH - ip.json gate_map is not regenerated for M1A and is internally inconsistent with the identity rule.**  
   Evidence: ADR says “ip.json gate_map regenerates for Phase A (this commit)” ([docs/adr/0026-m1a-performance-scope.md:53](/home/edauser/project/SOC/Magpie_M1A/docs/adr/0026-m1a-performance-scope.md:53)), but `ip.json` still maps `isa_scope` to `tests/gates/gate_00_spec.py` ([IP/cpu_m1/ip.json:170](/home/edauser/project/SOC/Magpie_M1A/IP/cpu_m1/ip.json:170)), and that gate asserts `design_id == "cpu_m1"` ([tests/gates/gate_00_spec.py:58](/home/edauser/project/SOC/Magpie_M1A/tests/gates/gate_00_spec.py:58)). The new M1A identity gate exists separately and asserts `cpu_m1a` ([tests/gates/gate_00_identity_m1a.py:20](/home/edauser/project/SOC/Magpie_M1A/tests/gates/gate_00_identity_m1a.py:20)). As written, the ADR’s “gate_00_identity_m1a enforces” claim is only partial; the active gate map still includes an M1 identity gate.

4. **MED - A3 says “AXI wrapper unchanged,” but this IP’s declared interface is valid/ready, not AXI.**  
   Evidence: ADR A3 says “AXI wrapper unchanged” ([docs/adr/0026-m1a-performance-scope.md:32](/home/edauser/project/SOC/Magpie_M1A/docs/adr/0026-m1a-performance-scope.md:32)), while `ip.json` declares only `imem`/`dmem` valid-ready manager interfaces ([IP/cpu_m1/ip.json:151](/home/edauser/project/SOC/Magpie_M1A/IP/cpu_m1/ip.json:151)), and `cpu_m1_top` is a Harvard single-outstanding valid/ready wrapper ([IP/cpu_m1/rtl/cpu_m1_top.v:2](/home/edauser/project/SOC/Magpie_M1A/IP/cpu_m1/rtl/cpu_m1_top.v:2), [IP/cpu_m1/rtl/cpu_m1_top.v:42](/home/edauser/project/SOC/Magpie_M1A/IP/cpu_m1/rtl/cpu_m1_top.v:42)). The spec explicitly says AXI/SoC adapters are out of v1 CPU IP scope ([IP/cpu_m1/docs/spec.md:42](/home/edauser/project/SOC/Magpie_M1A/IP/cpu_m1/docs/spec.md:42)). This should say “valid/ready wrapper unchanged” or define which AXI shell is in M1A scope.

ADR A3 targets ≥3.5 B/c and 64-bit fetch but only says retire compare is timing-invisible ([docs/adr/0026-m1a-performance-scope.md:32](/home/edauser/project/SOC/Magpie_M1A/docs/adr/0026-m1a-performance-scope.md:32)). 6. **MED - Baseline contradicts the ADR’s implied first scalar lever.**  
   Evidence: input evaluation ranks memory first and scalar second with “1-cycle MUL” ([docs/reports/m1a_performance_evaluation.md:40](/home/edauser/project/SOC/Magpie_M1A/docs/reports/m1a_performance_evaluation.md:40), [docs/reports/m1a_performance_evaluation.md:42](/home/edauser/project/SOC/Magpie_M1A/docs/reports/m1a_performance_evaluation.md:42)); baseline says “1-cycle MUL directly attacks 6.63 c/MAC” ([docs/reports/m1_benchmark_baseline.md:49](/home/edauser/project/SOC/Magpie_M1A/docs/reports/m1_benchmark_baseline.md:49)). Those are gate holes for an ISA-scope change.

8. **LOW - Vector phase uses a precise performance headline before locking the architectural/software assumptions.**  
   Evidence: ADR B promises Zve32x VLEN=128 dual-beat and “≥8 int8 MAC/c → 5.6 GOPS” ([docs/adr/0026-m1a-performance-scope.md:33](/home/edauser/project/SOC/Magpie_M1A/docs/adr/0026-m1a-performance-scope.md:33)), but later admits GCC 13.2 Zve32x support is still “to verify” ([docs/adr/0026-m1a-performance-scope.md:56](/home/edauser/project/SOC/Magpie_M1A/docs/adr/0026-m1a-performance-scope.md:56)).    Evidence: ADR context states parity already, ≈1729 vs ≈1680 ([docs/adr/0026-m1a-performance-scope.md:14](/home/edauser/project/SOC/Magpie_M1A/docs/adr/0026-m1a-performance-scope.md:14)). Baseline qualifies this as an engineering number: Verilator sim, ideal 1-cycle memory, DC-trial frequency, not EEMBC-reportable ([docs/reports/m1_benchmark_baseline.md:19](/home/edauser/project/SOC/Magpie_M1A/docs/reports/m1_benchmark_baseline.md:19)). ADR D4 should explicitly carry that caveat into any CoreMark claim.
